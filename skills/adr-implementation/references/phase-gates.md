# 阶段门禁与证据

## 单一阶段记录

优先复用项目已有阶段计划；避免为每个阶段复制一份进度表。至少能找到：阶段 ID 与代码身份、可观察结果、对应需求、允许范围与非目标、依赖、实现不变量、测试/审查/验收合同、状态转换和退出证据。ADR 只保留决策与阶段链接，测试合同管验证意图，验收记录管实际结果。

## 状态与上限

常规过程为 `PROPOSED → IN_PROGRESS → REVIEW_1 → ACCEPTANCE → PASSED`。审查指出问题时可进入 `REWORK_1 → REVIEW_2`，必要时再进入 `REWORK_2 → REVIEW_3`；最多两次修复、三次实现审查结论。第三次仍有未解决的合同缺陷则 `BLOCKED`，记录影响和恢复条件，不换阶段编号重置计数。

缺少授权、用户输入、外部服务、环境或证据时，分别记录 `WAITING_AUTH`、`WAITING_INPUT`、`EXTERNAL_HOLD`、`ENVIRONMENT_HOLD`、`EVIDENCE_GAP`；它们不是产品缺陷，但受影响阶段不能通过。下游依赖未过时保持未开始或 `BLOCKED_BY_<阶段>`；只有证明独立的工作可以继续。

## 通过与阻塞

- 每轮实现审查除本阶段差异外，也将累计变更和新增意见对照用户目标、范围基线与已授权变化，明确复用、旧行为回归和是否扩项；对显著扩张说明必要证据及较小可行备选。超出授权且并非达成目标所必需的变更，或显著扩张缺乏必要性论证且影响阶段出口时，应请求修改。不能把范围外旧债自动升级为本阶段阻断项，也不能忽略本次引入或为达成合同必须处理的缺陷。
- 审查聚焦本阶段差异、周边接口、安全、数据、并发、失败态和测试覆盖；结论只用 `PASS` / `REQUEST_CHANGES`，记录证据与处置。
- 验收记录准确的代码版本、环境、输入或操作、观察结果和局限；测试绿灯、按钮点击或任务 ID 都不能单独证明正式成果和外部结算。
- 每次状态变化记明原因、操作者、时间、代码身份和证据。`PASSED` 要求预定谓词全部满足并完成文档同步；证据失效时回到受影响门禁，不重做仍有效的已通过检查。
- 阻塞时分析根因或未知性、受影响接口与数据、下游依赖、可独立工作、已尝试方法、责任人和恢复条件。若需改变 ADR 合同，先回到决策阶段。

## 决策回退与恢复

实施中确认原 ADR 的持久合同或产品决定需要变更时，把当前受影响阶段记为 `BLOCKED_BY_ADR_REVISION`，记录触发证据、代码身份、已有未提交改动、已通过阶段及可能失效的下游成果。已 `PASSED` 的阶段保留其历史证据；只将受新决定影响的阶段标为“待重新核验”，不无证据地全局回滚或继续推进依赖阶段。

保留当前工作树及无关改动；是否隔离、提交或回滚，按项目规则、当前授权与精确目标另行决定，不把强制提交当作回退协议。主智能体将冲突与影响交给 `adr-writing` 修订方案，取得新的审查输入指纹和独立审查结论。同一决策的修订继续使用原审查轮次，不靠改编号或“增补 ADR”重置上限；确属用户新授权的独立决策，才建立新的审查周期。有效新方案确定后，从最早受影响阶段恢复，先重新验证血缘、接口和验收证据，再继续后续阶段。

## Git 与外部操作

遵循项目规定的规范主线和精确提交范围。若项目沿用串行主线工作流，在阶段通过且提交已获授权时完成该阶段的精确提交；隔离工作树是有依据的例外，集成后验证可达性及归属，再按项目规则关闭。保留无关更改，不使用重置、清理或强制操作制造通过状态。阶段完成、本地提交、推送和生产发布是四种不同声明。
