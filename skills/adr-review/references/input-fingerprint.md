# 方案审查输入与门禁记录

## 可复算的输入指纹

送审前列出 ADR、阶段计划、测试合同三类受检文件的仓库相对路径，分别对**原始文件字节**计算完整 SHA-256（64 位十六进制）。固定按 `ADR`、`PHASE`、`TEST` 顺序记录：

```text
ADR=<相对路径>@sha256:<64位摘要>
PHASE=<相对路径>@sha256:<64位摘要>
TEST=<相对路径>@sha256:<64位摘要>
```

多份 ADR 或合同时，同一类别按相对路径字典序列出全部文件，不得遗漏。阶段计划或测试合同若内嵌于 ADR，使用 `PHASE=embedded-in-ADR` 或 `TEST=embedded-in-ADR`；该内容由 ADR 摘要覆盖。缺少实施所需的阶段或测试合同不能写成“内嵌”，应在送审前补齐。不要以口头版本号、可变分支名、短哈希或未核对的提交号代替逐文件摘要。

主智能体在委派前计算并传入指纹；独立审查者重新计算并核对，无法读取或不一致时不得返回 `PASS`。实施前主智能体再次计算，与审查记录中获 `PASS` 的指纹逐项比较；任一受检文件字节变化，都不能直接沿用原 `PASS`，即使只是排版或错别字修正。

## 审查记录与状态变更

审查记录是独立于受检文件的唯一门禁记录，优先使用项目既有位置；没有时由主智能体建立一份最小记录，并在**送审前**从 ADR 链接。每轮记录受检指纹、代码身份、轮次、审查者、结论、定位意见及处置。独立审查者仅返回结果，不修改文件或写门禁记录。`PASS` 只证明所列输入版本通过方案审查，不代替用户实施授权。

审查结论、意见处置与实施就绪状态写入这份记录，避免写回 ADR 或合同造成指纹自失效。若项目规则要求审查通过后修改 ADR 状态字段，主智能体须保留修改前后完整摘要及精确差异；只有**状态字段这一机械变更**可沿用原审查结论，并把修改后摘要记作实施门禁核对值。正文、阶段、测试或其他元数据变化均须重新送审；不得把实质变更伪装为状态更新。

同一决策的首轮 `REQUEST_CHANGES` 后最多再审一轮。续行、换审查者、改文件名或另起同义增补文档都不重置轮次；第二轮仍未通过时停在方案门禁，向用户展示分歧及剩余风险。只有用户另行明确决定改变目标或启动真正独立的新决策，才为新决策建立新审查记录；不得以“新 ADR”绕过旧结论。
