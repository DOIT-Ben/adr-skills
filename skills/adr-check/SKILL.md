# ADR 架构影响检查

本组件只回答“现有代码能否承接这项新职责，以及新职责应放在哪里”。它向 ADR 提供事实和设计约束，不替用户决定需求，也不直接改代码。

## 输入和检查范围

取得目标行为、预计触及的入口或模块、项目规则与代码身份。范围不明时从当前调用链、现有设计文档及必要的代码搜索缩小范围；只追踪本次设计直接影响的调用者、被调用者、数据与测试。保留无关脏改动，不以全仓扫描或先修历史债作为前置条件。

## 证据检查

1. 对每个受影响模块记录文件、主要函数、近似规模、已有职责、对外接口、依赖方向和可复用入口。查看相邻代码与测试；不要仅凭文件名、注释或行数作结论。
   方案涉及定时任务、状态文件或外部执行器时，沿同一影响链核对运行入口、普通/事件调用方、实际读写者、字段粒度、数据保留和已有互斥能力；不扩成全站运维盘查。用源码、当前合同或必要运行证据说明能否复用；未核实的运行事实标缺口，不从名称推断语义。
2. 当声称“持续膨胀”或追究变更来源时，再查相关 Git 历史和职责演变；区分代码事实、变更时间和作者归因，证据不足时不推断责任人。
3. 判断是否存在职责混杂、协调过多阶段、循环依赖、宽接口、隐式状态或难以单独验证的集中逻辑。把 God Object/Class/Method 作为风险判断，不用固定行数一票否决。
4. 为每项新增职责提出归属：复用现有模块、建立一个内聚模块，或做有界抽取。说明接口、调用方向、必须留在原模块的职责、禁止继续堆入的行为，以及能验证边界的测试。需要跨领域取舍时列出备选，不代替 ADR 拍板。

## 输出合同

按 [影响报告格式](templates/impact-report.md) 给出受检代码身份、证据位置、风险等级、建议落点与不确定性。报告可直接供 `adr-writing` 引用；不修改代码、项目规则或实施状态。若发现范围外旧债，只记录影响和后续入口，不扩大当前 ADR。没有发现过载也要明确说明检查范围，不能把“没发现”说成全项目健康。
